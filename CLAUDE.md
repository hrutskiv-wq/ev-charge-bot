## 2. Файли рев'ю — правило власності

У корені лежать ~27 файлів `review_prompt*.md`. Усі в `.gitignore`, у git не трекнуті.
Це **не документація**, а вхідні дані рев'ю: дифф + тести + «де тут рухаються гроші».

Дві підгрупи, і різниця критична:

| Шаблон імені | Хто пише | Хто читає | Права Claude Code |
|---|---|---|---|
| `review_prompt-<назва>.md` | **Claude Code** | людина | створювати й перезаписувати можна |
| `review_prompt-<назва>-round2.md`<br>`review_prompt-<назва>-round3.md` | **людина** | Claude Code | **ТІЛЬКИ ЧИТАТИ. Ніколи не перезаписувати, не редагувати, не видаляти** |

Суфікс `-roundN` означає: файл написала людина у відповідь на попередній раунд.
Перезапис такого файлу знищує зауваження рев'юера, які ще не опрацьовані.
Якщо треба відповісти на `-round2` — створюй новий файл або пиши у відповідь у чат,
але **не чіпай сам файл**.

Правило додано після двох випадків перезапису протягом одного тижня.

## 3. Конвенції коду

- **Python 3.11**, FastAPI + uvicorn, aiogram 3, **asyncpg напряму — ORM немає**, сирий SQL у `app/database/`
- **Alembic — єдине джерело правди схеми.** Історично схему дублював ще й
  idempotent-бутстрап (`create_tables()` / `init_ocpi_tables()`) — вони вже одного разу
  розійшлися по enum `refund`. При зміні схеми оновлюй **обидва місця**, доки дубль існує.
  У новому коді (див. §4) — **тільки Alembic, без бутстрапу**
- **Гроші рухаються через одну точку.** `update_user_balance()` в `app/database/connection.py`
  атомарно оновлює кеш і журнал в одній транзакції. **Ніколи не писати напряму
  в `users.balance` або `kw_transactions` з інших модулів.** Це правило вже тричі
  порушувалось (OCPI CDR, Monobank webhook, Telegram-оплата) — щоразу з розсинхроном
- `SUM(kw_transactions.amount)` по користувачу **завжди** має дорівнювати `users.balance`
- **Bot/Dispatcher — єдиний екземпляр** з `app/core/loader.py`. Не створювати `Bot()` деінде
- `server.py` — не окремий застосунок, а шім (`from app.main import app`)
- **Секрети**: `OCPI_SECRET_TOKEN` навмисно валить імпорт, якщо не заданий — дефолтів немає.
  Перед `cat >> .env` перевіряй `tail -c1 .env | xxd` (файл має закінчуватись `\n`)

## 4. Архітектура: два продукти, одне ядро

Проєкт розділяється на дві лінійки. Стек той самий, покупець різний.

**A. Зарядки** (чинний `ev-charge-bot`) — OCPP 1.6J, еквайринг, ПРРО, кабінет оператора.
**B. Накопичувачі** (новий репозиторій) — оптимізація BESS за погодинними цінами РДН.

Цільова структура нового репо — **`evolt-bess`** (усе, що стосується накопичувачів,
має BESS у назві: репозиторій, документи `docs/BESS-*.md`, скрипти `bess_*.py`):

```
evolt-bess/
├── core/          # db · tenancy (org→site→device) · ledger · devices · notify
├── drivers/
│   └── modbus/    # huawei_smartlogger · sungrow_ems300 · deye · kstar
├── market/        # РДН: збір, зберігання, прогноз
├── optimizer/     # ЛП-рушій (є прототип: bess_backtest.py)
├── apps/
│   └── storage/   # advisory · диспетчеризація · звіти
└── migrations/
```

`drivers/ocpp16/` і `apps/charging/` лишаються тут, у `ev-charge-bot`, доки
не буде живого пілота BESS. Об'єднання ядер — крок 4 нижче, не раніше.

Деплой: **один образ, два entrypoint**, спільна Postgres.

### Порядок переїзду — послідовність важлива

1. **`ev-charge-bot` НЕ чіпати.** Він у проді, приймає реальні гроші,
   Model B (hold → finalize / cancel) пройшла бойову перевірку 30.07.2026
2. Новий репозиторій `evolt-bess`; `core/` спершу **копіюється**, не витягується
3. Пишеться `market/` + `optimizer/` + `apps/storage/` — чистий новий код
4. **Тільки після живого пілота BESS** — переводити зарядки на спільне ядро

Причина: до моменту злиття вже буде видно, як реально виглядає спільний
інтерфейс пристрою. Абстракція наосліп = переписування.

### Що спільне, а що ні

| Спільне | Тільки зарядки | Тільки накопичувачі |
|---|---|---|
| пристрій як абстракція (телеметрія + черга команд) | еквайринг, холди | ринкові дані РДН |
| леджер з єдиною точкою запису + реконсиляція | ПРРО / фіскальний чек | біддінг у XMtrade |
| мультитенантність, ролі | водійський веб-флоу | резерв під аРВЧ |
| **оптимізатор** (арбітраж BESS = зсув C&I = буферизована зарядка) | | |

## 5. Що вирішено

- **Гроші йдуть напряму на мерчант-рахунок клієнта.** Платформа коштів не торкається —
  немає платіжного посередництва, немає регулювання НБУ. Це єдина категорійна
  відмінність від усіх конкурентів (перевірено квитанціями: GO TO-U, TOKA, ECOFACTOR —
  у всіх отримувач сам оператор)
- **ПРРО = Checkbox.** Номенклатура «Послуги користування зарядною станцією», ПДВ 20%
  (підглянуто у фіскальному чеку TOKA)
- **Не інтегрувати банки поштучно — інтегрувати оркестратор** (Tranzzo / Fondy / WayForPay).
  Клієнт приносить свій мерчант-акаунт. Одна інтеграція замість N
- **Модель B (hold → finalize / cancel)** — водій платить за спожите, нічого не зависає
  в гаманці. Конкуренти вимагають поповнення наперед
- **Для накопичувачів базис порівняння — фіксований розклад, не цінова оптимізація.**
  Перевірено по мануалах: Deye (6 періодів), Huawei LUNA2000 (14 сегментів),
  KStar (7 профілів) — **поля ціни немає взагалі**. Динамічні тарифи в Huawei/Sungrow
  прив'язані до Nord Pool / EPEX / ESIOS / TGE / OTE — **України в жодному фіді немає**
- **Кабінет оператора — тільки Telegram.** Вебчастини для оператора немає і не планується
  найближчим часом. Вебфлоу існує лише для водія. Не додавати «оператор побачить у
  кабінеті» в жоден план чи пітч, доки це не змінилось
- **`ai_agent/` (CrewAI) лишається на майбутнє.** У прод не інтегрований, не видаляти.
  При цьому: **не тягнути в прод-образ** (`requirements-dev.txt` уже конфліктував
  `aiofiles` з `crewai`) і не тягнути його в контекст кодових сесій без окремого прохання

## 6a. OCPI — вимкнено 06.08.2026. Питання закрите

Вердикт після звірки коду **і** проду: **партнера-CPO ніколи не існувало**.
Роутери відключено, код і таблиці лишаються.

**Докази з проду (209.38.194.65):**

- `ocpi_cdrs` містить **3 рядки**, і всі три — власні тести:
  `cdr_prod_test_001`, `cdr_final_success_888`, `CDR-TEST-001`.
  Кожен списав `total_cost` замість `total_energy` (−610,20 при енергії 45,20;
  −450,00 при 30,50; −7,50 при 15,50) — тобто прилетів **до** виправлення 17.07
- `ocpi_locations` / `evses` / `connectors` / `tariffs` / `sessions` — **порожні**
- `OCPI_CPO_BASE_URL` у прод-`.env` **не заданий** → клієнт весь час ходив
  у `mock_cpo.py` на `127.0.0.1:8080`
- У логах за 30 діб — жодного звернення, крім ініціалізації таблиць
- CDR №4 посилається на `user_id = 12345`, якого в `users` немає: **зовнішній ключ
  `ocpi_cdrs.user_id → users(user_id)` у проді не діє.** Перший спостережений
  доказ розходження Alembic проти бутстрапу (§3)

**Що зроблено:** закоментовано `app/main.py:20-21` (імпорти),
`include_router(api_cdr_router)` і `dp.include_router(bot_stations_router)`.
`init_ocpi_tables()` на рядку 51 **лишено** — три CDR тепер доказова база.
886 тестів пройшли: усі OCPI-тести викликають функції модуля напряму,
а не через застосунок.

**Контроль після деплою:** `POST /ocpi/emsp/2.2.1/cdrs` віддає **405**, а не 404 —
бо `StaticFiles` змонтований на `/` останнім і приймає лише GET/HEAD.
401 означав би, що роутер ще живий.

**Побічний ефект:** без імпорту `app.api.ocpi` не завантажується `OCPIConfig`,
тому `OCPI_SECRET_TOKEN` більше **не валить старт**. Змінну з `.env` не прибирати —
`conftest.py` її досі виставляє.

**Що було підключено (історія):**

| Точка | Рядок | Що відкривало |
|---|---|---|
| FastAPI | `app/main.py:135` `include_router(api_cdr_router)` | `POST /ocpi/emsp/2.2.1/cdrs`, `.../callback/commands/START_SESSION/{user_id}`, `.../STOP_SESSION/{user_id}` |
| aiogram | `app/main.py:154` `include_router(bot_stations_router)` | команда `/ocpi` для **будь-якого** користувача |
| старт | `app/main.py:51` `await init_ocpi_tables()` | 6 таблиць створюються при кожному старті |

**Три речі, які треба тримати в голові:**

1. **`/cdrs` рухає гроші.** Викликає `update_user_balance()` і списує кВт·год
   з балансу водія за `user_id` із тіла запиту. Захист — один спільний статичний
   токен `OCPI_SECRET_TOKEN` (`secrets.compare_digest`). Ідемпотентність по `cdr_id` є.
   Поки партнера-CPO немає, це відкритий грошовий ендпоінт без жодного споживача
2. **Клієнтська частина дивиться в мок.** `OCPI_CPO_BASE_URL` за замовчуванням —
   `http://127.0.0.1:8080` (`mock_cpo.py`). У `.env.example` так і лишилось.
   Якщо на проді змінна не задана, `/ocpi` в боті б'є в неіснуючий мок
3. **`/ocpi` обходить FSM.** `StateFilter("*")` + `state.clear()` — команда
   переб'є будь-який стан, включно з незавершеною оплатою. `LOC-001` захардкоджено,
   `test_session_id` теж. У меню бота (`set_my_commands`) команди немає — але
   набрати її може хто завгодно

**Що справді мертве:** `app/services/ocpi/locations.py` оголошує
`APIRouter(prefix="/ocpi/cpo/2.2.1/locations")` з `PUT`, але цей роутер **не підключений
ніде**. `sync_locations.py` / `sync_commercial.py` — ручні скрипти, ні в cron, ні в systemd.

**Історія:** останній коміт по OCPI — **17.07.2026**, тим самим числом датований
`docs/PROJECT_CONTEXT.md`. Репозиторій живий до 03.08. Тобто OCPI не чіпали три тижні
активної розробки. У `PROJECT_CONTEXT.md` **20 згадок OCPI і жодної згадки OCPP** —
при тому що продукт працює на OCPP 1.6J. Документ описує етап, який закінчився.

**Пастка звірки, на яку варто зважати й далі:** перший запуск `check_ocpi.py` дав
хибне «роутери не підключені» — бо роутери імпортовані під псевдонімами
`api_cdr_router` і `bot_stations_router`, без слова `ocpi` в назві. Скрипт виправлено
(крок 3 тепер спершу збирає псевдоніми). Той самий патерн зіпсує будь-який
пошук по підрядку — не довіряти grep'у в питаннях «чи підключено».

## 6b. Що ще знайшлось на проді 06.08.2026

**Інваріант журналу був зламаний і відновлений.** Акаунт `514533557` (розробника):
баланс 70,00 при сумі журналу −787,70, розбіжність 857,70 кВт·год. Три причини,
усі липневі й усі вже виправлені в коді:

1. Шість рядків «Списання запуск зарядки» записані з **додатним** знаком замість
   відʼємного (баланс зменшувався правильно, журнал додавав). Того коду в репозиторії
   вже немає
2. Три OCPI-CDR списали `total_cost` замість `total_energy` **і не оновили баланс узагалі**
3. Два депозити (`add_deposit.py` і Telegram Invoice) потрапили лише в журнал

Виправлено одним рядком типу `correction` на +857,70 з поясненням в описі транзакції.
Ретроспективно правити 11 рядків не стали — це перепис історії заради косметики.
`update_user_balance()` тут навмисно **не** використовувався: треба було змінити лише
журнал, а функція такої гілки не має (`correction` потрапив би в `else` і списався б).

**Канонічний запит перевірки інваріанта — з `LEFT JOIN`, не `JOIN`:**

```sql
SELECT u.user_id, u.balance, SUM(t.amount)
FROM users u LEFT JOIN kw_transactions t ON t.user_id = u.user_id
GROUP BY 1,2 HAVING ABS(u.balance - COALESCE(SUM(t.amount), 0)) > 0.0001;
```

Версія з `JOIN` **не бачить** користувача, який має баланс і жодної транзакції.

**`payment_provider` не містив `telegram`.** На проді enum був `('liqpay','monobank')`,
бо створювався початковою міграцією, а не бутстрапом. При цьому
`app/handlers/user.py:1083` вставляє `provider='telegram'` — перша ж реальна оплата
через Telegram Payments впала б **після** списання грошей, без рядка в `payments`,
тобто невидимо для `reconcile_payments.py`. Не вибухнуло лише тому, що
`TELEGRAM_PAYMENTS_ENABLED` вимкнений. Закрито міграцією **0019**.

**Висновок, важливіший за три окремі баги.** Дубль схеми Alembic ↔ бутстрап
вистрелив уже **тричі**: `refund` (0008), відсутній FK на `ocpi_cdrs.user_id`,
`payment_provider` без `telegram` (0019). Правило в §3 не рятує — рятує тест,
який порівнює `pg_enum` і `information_schema` на базі з Alembic проти бази
з бутстрапу. Кандидат №1 у наступний бандл.
